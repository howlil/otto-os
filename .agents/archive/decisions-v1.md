# Otto OS engineering contract

## System

Otto OS is a single-process Windows shell surface hosting layered windows on the primary monitor plus the standalone `OttoSettings` top-level window:
1. `OttoNotchBar` + `OttoNotchPanel`: `OttoNotchBar` reserves the primary monitor's top strip via `AppBar` (`SPI_SETWORKAREA` fallback, DEC-26), hides the native Windows taskbar while configured, and renders a Clear Liquid Glass (DEC-57/DEC-75) macOS notch-style top bar with SF Pro typography and SF Symbol vector icons. Left side renders the Otto/Apple brand icon, active application name, and contextual menus (`File`, `Edit`, `View`, `Window`, `Help`) via `OttoPopupMenu`. Center Notch/Dynamic Island smoothly expands horizontally for Focus (Pomodoro/Timer/Stopwatch), Now Playing Media + Synced Lyrics, Call activity, or System HUD events, with dual-active compact secondary circle support (`HitTarget::NotchSecondary`, DEC-72) and expanded tabbed tools (`Focus`, `Media`, `Shelf`, `Clipboard`, `Tasks`, DEC-61). Right side renders `Tray Overflow → Status (Wi-Fi/Volume/Battery) → Search → Control Center → Notifications → Date/Time`; Notifications and Date/Time open independent popups.
2. `OttoDockBar`: renders a floating macOS bottom Dock with Finder, Launchpad/Apps, pinned and running applications (grouped 1 icon per executable via `decide_activation`), Downloads grid stack (`DownloadsStackRenderer`, DEC-74), a vertical divider, and dynamic Recycle Bin (`$Recycle.Bin` probe, DEC-59), supporting cosine hover magnification, bounce animation, badges/progress, drag-reorder/unpin, `WM_DROPFILES`, and Always/Auto-Hide/Reserve-Space modes (DEC-60).
3. Window Controls (`PluginId::WindowControls`, DEC-92): virtual feature (`surface: None`) rendering macOS `[Red (Close), Yellow (Minimize), Green (Zoom)]` circles directly inside `OttoNotchBar` (after the brand icon, before `AppMenu`) for the foreground window, with native client-area traffic lights drawn directly inside `OttoSettings`'s borderless-caption DWM Mica frame (`WM_NCCALCSIZE` + `WM_NCHITTEST`), Genie minimize (`OttoGenie` GPU worker, DEC-70), Alt+Click app-wide/fullscreen semantics, and Window Tiling menu — retiring the per-window `OttoWindowControls` floating cover overlays.
4. `OttoControlCenter`, `OttoSpotlight`, `OttoPopupMenu`, and `OttoSettings`: `OttoControlCenter` is a dedicated Clear Liquid Glass Bento popover (`ControlCenterRenderer`, DEC-75) for Connectivity, Focus, Battery, Display/Sound sliders, and Media; `OttoSpotlight` is a required local app search/catalog surface (DEC-76); `OttoPopupMenu` renders Top Bar, Dock, Window Tiling, Tray, Calendar, and Notification popups (`PopupMenuRenderer`); `OttoSettings` is a standalone DWM-backdrop top-level window (DEC-81) owning all settings and module plug-in/out controls.

## Structure and ownership

- `otto-core`: platform-independent domain models, layout/hit-testing, formatting, motion, glass composition, and capability ports organized by feature folder (`appearance/`, `bar/`, `control_center/`, `dock/`, `layout/`, `menu/`, `notch/`, `runtime/`, `settings/`, `spotlight/`, `window/`).
- `otto-platform`: Win32/COM/WinRT adapters organized by capability (`actions/`, `appearance/`, `bar/`, `control_center/`, `dock/`, `input/`, `notch/`, `settings/`, `spotlight/`, `system/`, `window/`).
- `otto-render`: Direct2D, DirectWrite, D3D11, and GDI resource ownership and feature drawers (`appearance/`, `bar/`, `control_center/`, `dock/`, `kit/`, `notch/`, `popup/`, `settings/`, `spotlight/`, `window/`).
- `otto-os`: process entry, `Host` lifecycle/runtime registry, centralized `win_msg` constants, architecture fitness tests (`host/fitness_tests.rs`), and feature controllers (`appearance/`, `bar/`, `control_center/`, `dock/`, `genie/`, `host/`, `menu/`, `notch/`, `settings/`, `spotlight/`, `window_controls/`).
- Within `otto-os`, the top-bar surface is composed by a root `Bar` orchestrator, `NotchController` + `NotchIo` for Notch features, and `BarControlsController` for non-Notch menu and status actions.
- Spotlight is a required host surface: `otto-os` owns its HWND, input, query state, focus, and motion; `otto-core` owns app-name ranking, selection, and resolved layout; `otto-platform` enumerates and launches `shell:AppsFolder` entries; `otto-render` paints the resolved surface. Its catalog is local applications only, with no file index or network search.

The dependency graph is:

```text
otto-os → otto-core
otto-os → otto-platform → otto-core
otto-os → otto-render → otto-core
```

No reverse dependency or platform dependency may enter `otto-core`.

## Shapes and flow

```text
Windows monitor/status/input
  → platform adapters
  → core values and resolved Layout
  → app-owned Bar state
  → render drawing and layered-window presentation
```

`Metrics` is the design input. `compute_layout` is the only layout resolver. `Layout` is the shared contract for rendering and hit testing. `HitTarget` is the only input result consumed by the app dispatcher. `SystemStatus` is a snapshot; the app refreshes the view only when the snapshot changes.

External application HWND state transitions remain native Win32 actions. For minimize and restore, the app presents a captured HWND snapshot through one bounded Genie overlay, commits its first frame, cloaks the source HWND, and performs the native state change with native transitions suppressed. Restore evaluates the exact inverse of minimize against the full snapshot; core Genie geometry and motion policy remain pure and reduced-motion-safe.

## State and execution

`Bar` owns the app bar registration, renderer, monitor snapshot, metrics, resolved layout, system status, hover target, and mouse tracking. The message loop is sequential on the window thread. Status polling is periodic, shell visibility is reasserted on each tick, and display or DPI changes rebuild the monitor-dependent renderer and layout before presenting again.

The process owns `InstanceGuard` for its lifetime. `AppBar` owns registration and taskbar restoration. `Renderer` owns Direct2D, DirectWrite, GDI, DIB, and DC resources and releases them through `Drop`. No spawned work may outlive the window thread without an explicit owner and cancellation rule.

Notch geometry is published for companion apps as the window property `OttoOS.NotchRect` (the island: the collapsed notch plus the secondary Focus or Media circle when visible, so its right edge is where a neighbor should dock) on the `OttoNotchBar` window: x (i16), y (i16), width (u16) and height (u16) packed little-endian into one 64-bit value, in bar-client physical pixels (the bar origin is the window origin). `otto-core` owns the encoding (`pack_notch_rect`, `unpack_notch_rect`), `otto-platform` writes it, and `Bar::recompute_layout` publishes only while the panel is collapsed and no press animation runs, so readers see the settled collapsed notch. A reader treats a missing or zero property as no published geometry.

## Failure policy

- Startup failures from window, app-bar, renderer, or required native resources propagate as `Result` and stop startup.
- Native flyout and shell calls are best effort; a failed call does not fabricate success.
- Blur is optional: if the OS rejects it, rendering continues with zero blur tint.
- A failed status query yields a safe default snapshot.
- A failed window capture or missing Dock target falls back to native minimize or restore and never leaves a visible overlay running.
- A failed presentation is transient at the runtime boundary; the next timer or state transition may retry it.
- No low-level Win32 or graphics error is exposed as a new domain protocol without an owning recovery policy.

## Design invariants

- All geometry is in physical pixels after DPI scaling from the `Metrics` point values.
- The bar spans the primary monitor width and uses the resolved notch and slot rectangles for both paint and interaction.
- Slot ordering is Start and application menus, Notch, then Tray, Status, Search, Control Center, Notifications, and Date/Time. Slots must remain within the bar, must not overlap the notch unexpectedly, and actions hidden by width pressure must remain reachable through Menu Overflow. Items the user hides through `menu_bar_hidden` have no slot and are not overflow entries; Otto Settings restores them (DEC-68).
- Render geometry, typography, colors, icon proportions, and hover treatment are owned by `otto-render`; their dimensions derive from `Layout` or named render constants.
- Platform modules perform native conversion and validation once. Core and render code operate on typed values rather than raw handles or Win32 structs.
- Unsafe blocks stay at the narrowest FFI or resource boundary. Resource acquisition, use, and release must be visibly paired in the owning type.

## Change rules

1. Search for an existing owner before adding a helper, constant, or abstraction.
2. Change one ownership boundary at a time and keep the dependency direction intact.
3. Add or update the cheapest faithful test for every changed core rule or failure policy.
4. Keep comments out of source. If a rule must be durable, update this contract instead of adding inline explanation.
5. Do not add a dependency, persistence layer, network path, service, or global state without an explicit contract and verification command.

## Decisions

- DEC-1: `otto-os` owns the transitional `Host` registry, surface creation, plugin configuration, and feature lifecycle; feature modules remain static Rust plugins until their boundaries are independently migrated.
- DEC-2: Runtime activation uses an allowlisted user-level plugin configuration at `%LOCALAPPDATA%\otto-os\plugins.txt`; Popup Menu and Spotlight remain required host surfaces and the Top Bar is required at startup unless the user turned it off (DEC-78).
- DEC-3: Platform-independent capability contracts begin in `otto-core`; Windows implementations remain in `otto-platform` and are injected into feature-owned state.
- DEC-4: Dynamic DLL loading is out of scope until static lifecycle, resource cleanup, ABI ownership, and failure isolation have release evidence.
- DEC-5: Windows media reads and commands run through a platform-owned COM worker with a short-lived cache; Host shutdown owns worker termination.
- DEC-6: Official Apple macOS HIG nomenclature ("Window Controls" with Close, Miniaturize, and Zoom/Full Screen) replaces legacy informal "traffic light" nomenclature across core, render, platform, and host modules while preserving backward compatibility for configuration parsing and transitional aliases.
- DEC-7: The top-bar Notch feature uses the `NotchPort` capability boundary for media, task-view, and Pomodoro-chime effects; `BarControlsController` remains snapshot/action based, while `Bar` owns menu anchors and platform execution. No renderer split or dynamic Notch plugin loading is introduced by this refactor.
- D-1: Optional plugin startup failures disable only that plugin and preserve the required host path; dependency violations are rejected before surface activation.
- D-2: Control Center is the first migrated capability boundary; its status, media, slider, and shell actions use `ControlCenterPort`.
- D-3: Plugin configuration writes use a platform-owned write-through replacement so a process or machine interruption does not leave a partial config file.
- DEC-8: Adaptive Clear Material System. `ThemeMode` and `ResolvedTheme` remain compatibility and semantic-ink types, while `otto-render::GlassPainter` selects white or graphite ink per captured surface using backdrop luminance hysteresis. `LiquidGlassPalette` provides one clear optical material; no public Light/Dark/Opaque appearance selector exists. Windows transparency, blur support, and high contrast own opaque accessibility fallback selection. The Center Notch and Dynamic Island stay Obsidian Black (`#000000`) across all ink states.
- DEC-9: Legacy theme command and config identifiers remain readable for compatibility, but do not override runtime appearance; Control Center, Display, Otto Settings, and the Apple menu do not expose theme or glass-material switching. Active glass surfaces repaint from their own backdrop-adaptive appearance, and non-glass fallback follows the Windows system appearance.
- DEC-10: OS Event Single Source of Truth & Windows OSD Suppression. Low-level keyboard hook (`WH_KEYBOARD_LL`) in `otto-platform::os_events` intercepts native multimedia keys (`VK_VOLUME_UP`, `VK_VOLUME_DOWN`, `VK_VOLUME_MUTE`). When intercepted, Otto OS applies direct WASAPI scalar volume adjustments and returns `LRESULT(1)` to suppress the Windows Explorer volume flyout. In addition, periodic maintenance suppresses and hides native Windows on-screen displays (`NativeHUD`), ensuring Otto OS Notch HUD remains the sole source of truth for volume and mute feedback.
- DEC-11: Event-Driven Window Controls & Adaptive Animation Timer. `otto-platform` installs a Win32 out-of-context hook (`SetWinEventHook`) filtering for `EVENT_SYSTEM_FOREGROUND` and `EVENT_OBJECT_LOCATIONCHANGE` with `OBJID_WINDOW` and `WINEVENT_SKIPOWNPROCESS`. Events are posted directly to the WindowControls surface (`WM_APP_WINDOW_SYNC`), eliminating continuous 25ms polling and GDI titlebar pixel sampling while idle. When the target window moves or foreground transitions occur, an adaptive 16ms animation timer is armed to drive smooth cubic follow motion and titlebar sampling until the overlay reaches rest and settles (`settle_ticks == 0`), upon which `KillTimer` disarms the loop to ensure 0% idle CPU usage.
- DEC-17: Apple Dynamic Island 3-Tier Notch Media Layout, Interactive Scrubber, and DirectWrite Trimming Invariants. To resolve text and control collision when titles or lyrics are long, the expanded media notch layout (`Metrics::MACBOOK_PRO_14.notch_expanded_height: 144`) is strictly divided into three vertically segregated tiers:
  1. Header Tier (y: 36..80): 44x44 squircle cover art, song title and artist/album, and live right-aligned audio equalizer glyphs. Title and artist text formats enforce DirectWrite `DWRITE_TRIMMING_GRANULARITY_CHARACTER` with `CreateEllipsisTrimmingSign` and `D2D1_DRAW_TEXT_OPTIONS_CLIP`, ensuring glyphs never bleed into neighboring widgets.
  2. Scrubber Tier (y: 90..104): Full-width interactive seekbar backed by Windows GSMTC `TimelineProperties` (`position_ms`, `duration_ms`). Left side displays elapsed time (`mm:ss`) and right side displays remaining time (`-mm:ss`). Click interactions hit `HitTarget::MediaSeekbar`, mapping relative horizontal position to milliseconds and emitting `MediaCommand::Seek(target_ms)` through `TryChangePlaybackPositionAsync`.
  3. Controls Tier (y: 110..140): Centered playback control triad (Previous, Play/Pause 34px button, Next), avoiding horizontal collision with text and maintaining visual balance.
- DEC-18: Direct2D Resource Palette and Notch Geometry Caching. To eliminate per-frame Direct2D COM object allocation churn (`CreateSolidColorBrush` and `CreatePathGeometry`), all renderers (`Renderer`, `DockRenderer`, `PopupMenuRenderer`, and `WindowControlsRenderer`) utilize pre-allocated persistent brushes (`BrushPalette`) with in-place `SetColor(&color)` mutation alongside an 8-slot scratch brush pool for ephemeral tinting. Top bar and panel notch bezier path geometries are cached in `CachedNotchGeometry`, matching on bitwise-exact dimensions (`Rect`, `corner_radius_bits`, `ear_radius_bits`) and returning cloned COM pointers (`ID2D1PathGeometry`) with zero-allocation atomic `AddRef` instead of rebuilding and tessellating bezier geometry sinks every frame.
- DEC-19: Hybrid Hardware-Accelerated Window Capture & Black-Box Detection for Genie Effect. To prevent black box rendering during Genie animation of modern GPU-accelerated applications (Chromium, Electron, Discord, VS Code), `capture_window` in `otto-platform` implements a hybrid capture pipeline with client-area black box detection:
  1. `PrintWindow` with `PW_RENDERFULLCONTENT` is attempted first.
  2. The captured DIB is validated by pure function `is_blank_frame(width, height, pixels)` in `otto-core`, using a 25-point sampling grid concentrated in the client area ($X \in [15\%, 85\%]$, $Y \in [20\%, 80\%]$) to catch the classic Chromium bug where GDI renders non-client borders but leaves the client area completely black.
  3. If unrendered/blank and the target window is the active foreground window (`GetForegroundWindow() == hwnd`), a secondary `BitBlt` from `screen_dc` captures the live GPU-composited screen surface at the window's physical bounds, followed by a re-check with `is_blank_frame`.
  4. If both capture attempts fail or yield blank pixels (or if a background window cannot be captured cleanly), `capture_window` returns `None`, allowing `minimize_window_to` to execute a clean native Win32 minimize without spawning a corrupted or pitch-black Genie overlay.
- DEC-20: Authentic macOS Top-Left Window Controls & Top Bar Overlap Invariant. Window controls are anchored to the top-left of the active window with macOS sequence [Red (Close), Yellow (Minimize), Green (Zoom/Fullscreen)]. Artificial opaque cover plate background rendering is removed in favor of transparent per-pixel alpha drawing. Vertical positioning enforces the invariant y >= bar_height, with controls hidden when the target window's titlebar is occluded behind OttoNotchBar, ensuring OttoWindowControls never occludes top-bar slots or intercepts Clock / Control Center clicks. Left-click on Green executes Zoom/Maximize within workspace bounds, Alt-click executes Fullscreen (F11), and right-click opens the macOS Window Tiling menu.
- DEC-21: Authentic macOS Dock Active Application Click Semantics. Clicking an active/foreground application tile in OttoDockBar no longer minimizes the application to the Dock (reversing Windows taskbar minimize-toggle semantics). Instead, it preserves authentic macOS behavior by asserting focus on the application and bringing its windows to the front, reserving minimization solely for explicit user intent via the Yellow traffic light, shortcut (Win+Down / Cmd+M), or context menu.
- DEC-22: Authentic macOS Dock Sector Separation, Downloads Stack, Drag Reorder & Drop Target. Left sector contains running and pinned applications; right sector contains Stacks (Downloads) and dynamic Trash separated by a vertical divider line. Pinned applications support drag-and-drop reordering with persistent atomic serialization (`pinned.txt`) and drag-out poof unpinning (drag distance $\ge 45\text{pt}$ into desktop). Hidden applications (`Cmd+H` or minimized cloaked state) are visually dimmed to 55% opacity with 45% alpha indicator dots. Native `WM_DROPFILES` integration enables dragging files from Windows Explorer onto Dock application tiles to launch directly with that application, or onto Trash to recycle via `SHFileOperationW`.
- DEC-55: Lyrics depth-of-field uses soft-edge ring sampling. The notch panel draws through an `ID2D1DCRenderTarget`, which has no effects pipeline, so inactive lyric lines are blurred by drawing the text once at half alpha and eight times on a ring whose radius grows with distance from the active line (`lyric_blur_radius`, up to 0.9 px at 96 dpi). The active line is never blurred. Moving to `ID2D1DeviceContext` and `GaussianBlur` is the replacement path if a real blur is required.
- DEC-56 [two-way]: Window controls always cover the right-hand caption buttons and never fall back to a left-anchored set, because a second set beside the app's own buttons shows two controls at once. The cover width is the DWM caption-button width when it is within 75%-125% of the standard 46 DIP per slot, otherwise the standard width; a window with `WS_CAPTION` and `WS_SYSMENU` whose DWM bounds are unavailable gets a standard-height caption (30 DIP) at the visible frame top-right; a window without a system menu has no buttons to cover and gets no controls; elevated windows (`WindowInfo::traits.elevated` / UIPI-blocked processes detected via `is_window_uipi_blocked`) are excluded from overlay targeting and `native_minimize` when Otto runs non-elevated so native buttons and drag keep working, while their bounds stay recorded as occluders. Inside the full cover span, the three circles (`[Minimize (Yellow), ToggleMaximize (Green), Close (Red)]`) sit on the right (`20 DIP` center-to-center, `6 DIP` radius, `14 DIP` right margin) and execute on macOS press-and-release (`PressState` + mouse capture `SetCapture`, darkened fill/border while held, cancel if pointer leaves the circle before `WM_LBUTTONUP`). In the covered area left of the circles, click-1 focuses the window without restoring minimized state (`activate_window_no_restore`) and defers native `WM_NCLBUTTONDOWN(HTCAPTION)` drag until pointer movement exceeds `SM_CXDRAG`/`SM_CYDRAG` so click-1 focus and double-click Zoom stay clean; right-clicking empty cover forwards `WM_NCRBUTTONUP(HTCAPTION)` for the native system menu. On resizable unmaximized windows, a `4 DIP` outer strip along the top, top-right, and right edges outside the circles (`ResizeEdge`) maps to native resize cursors and forwards `HTTOP`/`HTTOPRIGHT`/`HTRIGHT` (`forward_resize_drag`). Overlays stay visible until `caption.top + caption.height <= bar_height` (`window_controls_visible_under_bar`) so the `HWND_TOPMOST` notch bar clips partial top overlap naturally. To blend with 0% idle CPU, `otto-platform::sample_caption_strip` captures a `24 DIP` strip clipped below `min_top` via one `BitBlt` when unobstructed by `sample_occluders`; `otto-core::extract_cover_rows` votes smooth vertical gradient clusters to resist tab/icon outliers, renders with a `6 DIP` left alpha feather (`COVER_FEATHER_DIP`), applies `top_border_inset` only when `rounded_top_right && buttons.top <= 0`, adapts inactive circle luminance (`cover_is_dark`) to dark vs light titlebars, and runs bounded event-driven settle resampling on foreground change, `EVENT_OBJECT_NAMECHANGE` (`OverlaySync`), and appearance changes. Overlays omit `WS_EX_TOPMOST` and `place_overlay_above` keeps each overlay immediately above its target HWND in z-order (matching topmost vs non-topmost band), refreshed on `EVENT_OBJECT_REORDER`. `otto-platform::visible_window_targets` drops an overlay only when an above normal window fully contains its cover (`contains_rect`), preserving overlays under partial left-edge overlap so upper windows/menus cover overlays naturally without exposing native buttons. `otto-os` keeps a pool of up to 25 layered overlays (the host surface plus up to 24 spawned without `WS_EX_TOPMOST`) assigned stably by `hwnd`.
- DEC-57 [two-way]: Liquid glass for the bar, Dock, Control Center, and Popup Menu is composed by Otto from a captured backdrop instead of DWM acrylic or Mica. Spike evidence (Windows 11, 26200): a layered NOACTIVATE window gets a solid fill from every DWM backdrop path while Battery Saver is on, DWM blur fills the whole window rectangle rather than the alpha shape, and the Dock window also carries tooltips and magnified icons that a window region would clip. A captured backdrop has none of these limits. `otto-core::glass` holds the pure pipeline (`RgbBuffer` downsample, 3-pass sliding-window box blur, adaptive luma-compression + chroma-aware vibrancy grade, and $C^1$ Hermite `smoothstep` texel sampling; `GlassShape` signed distance with fast axis-aligned interior path; fixed `LIGHT_DIRECTION` (the rim light never tracks the pointer, so hover causes no glass recompose); `compose_glass_lit` with curved 18 pt bezel / 14 pt shift, RGB chromatic dispersion across `backdrop.sharp`, upper sheen, inner shadow, inner bevel glow, and directional dual-specular rim `rim_base`/`rim_lit`/`rim_bounce`, and outline) and the per-theme `GlassParams` (`tint_amount` 0.22 Dark / 0.32 Light); Dark and Light differ only in parameters. Interior text contrast is checked in tests against the brightest and darkest possible backdrop for primary text, and against 0.25 to 0.75 mid-tone backdrops for muted text; muted text over a pure-black wallpaper in the Light theme is not guaranteed and is left to adaptive tint. `otto-platform::backdrop` owns capture: `BackdropWorker` runs one BitBlt with CAPTUREBLT per request on its own thread (the call waits for vsync and costs about 16.6 ms at any size), keeps only the newest pending request and the newest frame, and wakes the owner through a notify callback; `exclude_from_capture` and `include_in_capture` set WDA_EXCLUDEFROMCAPTURE on Otto's bar, Dock, Control Center, and Popup Menu windows (without it the glass would photograph itself, a fact checked by an ignored native fixture). Capture coordinates are physical pixels, so the process must be per-monitor DPI aware or the region lands on the wrong pixels. Battery Saver is read from `SystemStatusFlag` and folded into `SystemAppearance.transparency`, so the existing Opaque variant is the solid fallback. `otto-render::glass` and `otto-render::glass_gpu` turn a capture into pixels: `GlassComposer` (cached by backdrop generation, theme, DPI, shape, lens flag, and the fixed light vector; `BASE_SOFT_FACTOR = 2` and point-constant `BASE_BLUR_PT = 9` radius with `MIN_BLUR_RADIUS = 3` scaled against `soft_factor(dpi)`) blurs the backdrop via `soften_backdrop` and composes the lit bevel/dispersion/rim on D3D11 using compiled HLSL shaders (`liquid_glass_vs.dxbc` / `liquid_glass_ps.dxbc`) owned on the composer instance rather than `thread_local!` storage, caching `sharp`/`soft` `R32G32B32A32_FLOAT` SRVs per capture and falling back to CPU `compose_glass_lit` if D3D11 is unavailable; `GlassPainter` uploads the bitmap once per revision and draws it under the content; the bar bleeds `22 pt` (`> lens_band + shadow_depth`) off the top/left/right screen edges with `lens = true` so only its bottom bevel refracts, while Dock, Control Center, and Popup Menu draw lensed shells, falling back to solid/translucent fills (`bar_background`, `dock_fill`, `menu_fill`) whenever no backdrop is set or the appearance is Opaque or high contrast. Native tests verify that GPU composition and drawn surfaces match the core reference within 3 levels per channel. Any render test that draws a bitmap must end with `release_shared_factories()` after dropping its target, otherwise the test thread hangs at exit on the thread-local Direct2D factory. `otto-os` feeds the renderers: `BackdropFeed` owns one `BackdropWorker` per surface (bar, Dock, Control Center, Popup Menu) and wakes the surface window with a private message when a frame is ready; `otto-core::capture_plan` holds the pure rules (`CaptureRegion::clipped_to_screen` and `CaptureRegion::padded_to_screen`, `CaptureGate` that throttles requests and accepts a frame once per signature, `capture_interval_for`: 33 ms active / 400 ms calm, or 120 ms active / 1,000 ms calm on battery, `capture_wanted`). Surfaces capture their regions padded by `24 pt` (clipped to the screen) so edge blur and lens refraction sample surrounding pixels, forced again when window geometry changes, and DWM acrylic calls on bar, Control Center, and Popup Menu are removed. Otto windows are excluded from capture only while capture is active, so Opaque, high contrast, Battery Saver and `--no-blur` keep Otto visible in screenshots. Appearance is re-read on power events and about once a second so Battery Saver changes take effect. Consequence to accept: Otto windows do not appear in screenshots or screen recordings while exclusion is on. Battery Saver and disabled transparency must fall back to the solid `dock_fill`, `bar_background`, and `menu_fill` colours.
- DEC-58: Background Cleanup throttles sustained background CPU hogs, audits running processes and memory buffers in `OttoSettings -> General`, and never auto-terminates processes. The `background_cleanup` preference (default off, `Background Cleanup` row in Otto Settings, persisted in the preferences file) starts the platform-owned `otto-cleanup` worker in `otto-platform::background_cleanup`; disabling it stops and joins the worker and restores every auto-throttled process, while `shutdown_background_cleanup` (`shutdown_background_tasks`) stops the worker and restores both auto- and manually-throttled processes (`auto_origins` and `manual_origins` inside shared `CleanupState`). While on, the worker samples every `HOG_SAMPLE_INTERVAL_SECS` (10 s) via Toolhelp and `GetProcessTimes`. A process is considered only if the current token can open it with `PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_SET_INFORMATION`, `session_id != 0`, and `IsProcessCritical` is false, which excludes services, elevated, and other-user processes. `otto-core::process_hog::HogTracker` owns the automatic throttling policy (20% of one core for 4 consecutive samples, foreground family + `explorer.exe`/`dwm.exe`/`otto-os.exe` exempt), setting EcoQoS (`ProcessPowerThrottling` / `PROCESS_POWER_THROTTLING_EXECUTION_SPEED`) and lowering `NORMAL`/`ABOVE_NORMAL` to `BELOW_NORMAL` priority with PID creation-time verification on restore. For auditability and user control, `otto-core::process_hog` also owns pure process grouping and three-tier safety classification (`classify_process_protection`, `summarize_process_audit`, `ProcessSafety::{SafeBackground, ActiveWindow, SystemProtected}`, `ProtectionReason`): OS critical processes (`IsProcessCritical`, PID <= 4, `csrss.exe`, `lsass.exe`, `smss.exe`, `wininit.exe`, `services.exe`, `winlogon.exe`, `fontdrvhost.exe`, `System`, `Registry`, `Memory Compression`), Session 0 Windows services (`svchost.exe`, `spoolsv.exe`, `audiodg.exe`, `msmpeng.exe`, `securityhealthservice.exe`, `wudfhost.exe`, `searchindexer.exe`, `conhost.exe`, `dllhost.exe`, `runtimebroker.exe`), desktop shell (`explorer.exe`, `dwm.exe`, `sihost.exe`, `taskhostw.exe`, `shellexperiencehost.exe`, `startmenuexperiencehost.exe`, `searchhost.exe`, `textinputhost.exe`, `ctfmon.exe`, `applicationframehost.exe`), `otto-os.exe`, and elevated/system-token processes are locked as `Protected`; foreground application families (`ActiveWindow`) allow manual EcoQoS only; and non-foreground user apps (`SafeBackground`) flag hidden memory buffers (`!has_visible_window && memory_bytes >= MEMORY_BUFFER_THRESHOLD_BYTES` 100 MiB), background CPU hogs (`>= 5.0%`), and strict `Safe to End` candidates (`SafeBackground && can_terminate && !has_visible_window && memory_bytes >= SAFE_TO_END_MEMORY_THRESHOLD_BYTES` 150 MiB excluding known cloud-sync, VPN, peripheral, GPU/audio, and WSL/Docker daemons), exposing explicit user-triggered `EcoQoS`/`Restore` (`toggle_process_group_throttle`) and safe `End Task` (`terminate_process_group`, restricted to controllable non-foreground headless/background user processes) in `SettingsPage::General` (`otto-core::settings::general_settings`, `SettingsRowValue::ProcessAudit`) with a 2 s `AUDIT_TIMER_ID` refresh that pauses while hovering rows or buttons. Rejected on purpose: automatic termination, `EmptyWorkingSet` and standby-list purging, and telemetry/network reporting.

## Modular system contract

The target is a modular monolith, not a service graph or a runtime DLL ecosystem. A feature is replaceable when its state, native effects, renderer, and lifecycle are behind one narrow entry point. A feature is not replaceable merely because it has its own Rust file.

### Responsibilities and state ownership

- R1 Host composition: `otto-os::host` owns descriptors, dependencies, activation, surface registration, configuration, and shutdown ordering.
- R2 Feature runtime: each feature owns its controller state and dispatches typed core events to domain effects. It may not create, destroy, or mutate a sibling feature.
- R3 Core policy: `otto-core` owns domain values, layout, hit testing, motion, menu models, and capability contracts. It never owns Win32 handles or render resources.
- R4 Platform adapters: `otto-platform` owns Win32, shell, hooks, COM workers, persistence adapters, and native resource conversion. It returns domain values or explicit failure/absence.
- R5 Render adapters: `otto-render` owns Direct2D, DirectWrite, GDI, layered-window presentation, and feature drawing. It consumes core values and never invokes platform actions.
- S1 Host lifecycle | owner `Host` | every required surface starts before dependants; every feature stops before its HWND is destroyed; concurrent writers: window thread only.
- S2 Feature state | owner of the feature runtime | derived layout can be recomputed from core inputs; no second mutable owner; concurrent writers: owning window thread.
- S3 Native hooks and workers | owner of the platform capability that created them, with shutdown called by `Host` | unregister/terminate before owner teardown; no callback may target a stopped surface.
- S4 Render resources | owner of the renderer instance | acquisition, use, and `Drop` remain paired; no feature creates a second device/resource lifetime without a contract.
- S5 Plugin configuration | owner `PluginConfig` plus the atomic file adapter | unknown optional entries are ignored, required entries are restored, and a failed write does not replace the last valid file. Durability target remains A1.

### Contracts and critical flows

- K1 `Host -> feature`: descriptor and dependency state enter `start`; result is `Running` or isolated `Failed`; `stop` is idempotent and releases hooks/timers before `Host` destroys the surface.
- K2 `feature -> core`: typed snapshots, hit targets, actions, and effects cross the boundary; raw HWNDs and Win32 structs do not.
- K3 `feature -> platform`: use a capability-scoped port or adapter such as `NotchPort` or `ControlCenterPort`; do not create a mega `PlatformPort`.
- K4 `feature -> render`: resolved `Layout` and feature snapshots enter a renderer; the renderer returns presentation failure without performing native policy.
- K5 `PluginConfig`: `version=1` and an allowlist are the compatibility contract. Future versions accept N-1 during migration, preserve required plugins, and ignore unknown optional names.
- Startup: config -> dependency validation -> required surfaces -> optional feature start -> running message loop. A required failure aborts startup; an optional failure disables only that feature.
- Runtime enable/disable: request -> dependency check -> feature start/stop -> state update -> atomic config write. On failure, the prior running/config state remains the valid outcome.
- Shutdown: stop event sources and feature controllers -> destroy feature HWNDs -> restore shared shell state -> stop platform workers. Stale native messages are ignored after feature state is gone.

### Guarantees and challenge

- G1 [H]: when an optional feature fails to start or stop, required Top Bar and Popup Menu behavior remains available and the feature is marked disabled; measured by app lifecycle tests and Windows smoke acceptance.
- G2 [H]: when a feature is stopped, hooks, timers, workers, renderer resources, and owned HWNDs are released in dependency order; measured by lifecycle tests plus Windows resource/hook acceptance.
- G3 [H]: when layout is recomputed, rendering and hit testing consume the same core `Layout`; measured by core geometry tests and app input/render integration checks.
- G4 [M]: when a platform call is absent or fails, the feature receives `Option`, a safe snapshot, or an explicit error according to its port contract; it never fabricates native success.

| Flow | Failure | Blast radius | Containment and recovery |
|---|---|---|---|
| Optional start | surface, renderer, or adapter init fails | one feature | mark `Failed`, destroy only its surface, retain required host path |
| Stop/shutdown | hook callback, timer, or worker outlives feature | feature and possibly process teardown | unregister/cancel first, then destroy HWND; host owns final worker shutdown |
| Config write | interruption during replacement | future activation only | keep previous valid file; load defaults and required plugins when unreadable |
| Capability call | Windows API or external app state unavailable | current interaction | return absence/default/error; native source of truth remains authoritative |

## Assumptions and risks

- A1 [blocking for dynamic plugins or independent deployment]: no `.agents/product.md`, runtime hot-reload requirement, third-party plugin ABI, availability target, or performance SLO is defined. This contract therefore assumes one process, statically linked Rust features, one UI thread, and no independent deployment. Decide these requirements before choosing DLLs or services.
- A2: Windows-native capture, DWM timing, hooks, and visual continuity require manual acceptance on Windows; compile and unit tests cannot prove them.
- Risks / trade-offs: host composition is intentionally centralized; current platform/render files have high change fan-out; static linking gives reliable resource ownership but limits external runtime extensibility.

- DEC-43 [two-way]: Media session model (M10.1). `otto-core::NowPlaying` carries `source_app` (SMTC `SourceAppUserModelId`), `position_updated_unix_ms` (timeline `LastUpdatedTime`), `playback_rate_permille`, and `MediaCapabilities` (play/pause, next, previous, seek from the session's playback controls). - DEC-44 [two-way]: Media commands and seeking (M10.2, M10.5). The media worker awaits each SMTC `Try*Async` reply within the 1.5 s operation deadline and classifies it as accepted, rejected, no session, or timed out; anything but accepted plays the command-failure signal.
